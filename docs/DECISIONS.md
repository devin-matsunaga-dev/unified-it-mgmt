# DECISIONS.md — Decision Log

> One line per settled choice: "chose X over Y because Z (WP-N.N, date)". Appended by Codex at the end of every session; never relitigated without a work package.

- Bootstrap: platform versions pinned to LTS/latest-supported — .NET 10, Aspire 13.x, Node 24, Python 3.13+ (see WORKFLOW.md table)
- Bootstrap: UI = Tailwind + shadcn/ui + lucide per DESIGN.md reference screenshot

- WP-0.2: no new architectural decisions; infrastructure follows the resource topology already settled in ARCHITECTURE.md (2026-08-06)
- WP-0.3: no new architectural decisions; bearer authentication, policy authorization, and provider-neutral configuration follow the existing authentication architecture (2026-08-06)
- WP-0.4: no new architectural decisions; append-only auditing, notification logging, and scheduled jobs follow the existing platform-service architecture (2026-08-06)
- WP-0.5: chose MassTransit 8.5.10 over 9.x because 9.x requires a commercial runtime license; EF transactional outbox and deterministic consumer deduplication remain unchanged (2026-08-06)
- WP-0.6: chose oidc-client-ts with authorization-code PKCE and automatic silent renewal because it keeps the SPA provider-neutral and stores tokens only in session storage (2026-08-06)
- WP-0.7: chose GitHub Actions with GHCR tag publishing because the repository is hosted on GitHub and can authenticate image pushes without additional credentials (2026-08-06)
- WP-0.8: no new architectural decisions; the console seeder and realm-import users follow the existing Platform and Keycloak development topology (2026-08-06)
- WP-1.1: no new architectural decisions; ticket storage, auditing, and event publication follow the existing module-schema and Platform outbox architecture (2026-08-06)
- WP-1.2: no new architectural decisions; persisted workflow configuration, guarded transitions, history, auditing, and outbox publication follow the existing Helpdesk and Platform patterns (2026-08-06)
- WP-1.3: no new architectural decisions; team-owned queues, persisted round-robin state, assignment history, auditing, and technician-scoped queries follow the existing Helpdesk patterns (2026-08-06)
- WP-1.4: chose a 25 MB attachment ceiling with an explicit document/image/archive extension and media-type allowlist because the required 10 MB upload needs headroom while executable and unknown formats must fail closed (2026-08-06)
- WP-1.4: chose private MinIO objects served through authorized API downloads because ticket visibility must be enforced for every attachment access (2026-08-06)
- WP-1.5: chose persisted elapsed business seconds plus an active interval over wall-clock deadlines because Pending pauses and calendar changes must not consume SLA time (2026-08-07)
- WP-1.5: chose a per-policy warning percentage constrained to 1–99 because different service tiers need configurable lead time before breach (2026-08-07)
- WP-1.5: chose priority-only matching for currently uncategorized tickets while persisting an optional category selector because ticket categories are introduced by WP-1.9 (2026-08-07)
- WP-1.5: chose resolution-breach reassignment to the next ordered queue technician because it extends the established round-robin ownership model without adding a second escalation topology (2026-08-07)
- WP-1.6: chose MailKit 4.17.0 for IMAP, MIME parsing, and SMTP because it provides maintained protocol support and passes the repository vulnerability gate (2026-08-07)
- WP-1.6: chose unique RFC Message-ID persistence with stable ticket Message-ID headers and subject-token fallback because retries must be idempotent and replies must thread across mail clients (2026-08-07)
- WP-1.6: chose MailHog for outbound capture plus GreenMail for the development IMAP inbox because MailHog does not provide IMAP retrieval (2026-08-07)
- WP-1.7: chose an idempotently seeded Service Desk queue with development technician usernames because agent assignment must be verifiable in a fresh Aspire environment without manual API setup (2026-08-07)
- WP-1.7: chose to persist a comment-author display-name snapshot alongside the immutable identity ID because timelines need human-readable attribution without coupling Helpdesk reads to an identity provider (2026-08-07)
- WP-1.7: chose the same display-name snapshot pattern for ticket requesters because ticket headers need readable attribution while ownership checks continue using immutable identity IDs (2026-08-07)
- WP-1.7: chose to snapshot the requester email separately from the identity ID because lifecycle notifications require a stable SMTP recipient and must never treat an OIDC subject as an address (2026-08-07)
- WP-1.7: chose to email only public comments authored by agents because internal notes must remain private and EndUser/inbound-email comments must not create mail loops (2026-08-07)
- WP-1.8: chose a separate `/portal` route tree with its own top-nav shell restricted to the EndUser role over reusing the agent AppShell because requester scoping only exists for EndUsers and an agent inside the portal would see every ticket as "mine" (2026-08-07)
- WP-1.8: chose to render the portal submit form's request picker from the existing Incident/ServiceRequest type rather than adding a ticket category column because categories are WP-1.9's scope and a flat interim string would need rework (2026-08-07)
- WP-1.8: chose to restrict EndUser transitions server-side to Resolved→Closed (403 ProblemDetails otherwise) because close-confirm must be enforced below the UI, not by hiding buttons (2026-08-07)
- WP-1.8: chose to route portal submissions to the seeded Service Desk queue by name, falling back to the first queue then unqueued, because self-service tickets must enter round-robin assignment without asking requesters to pick a queue (2026-08-07)
- WP-1.9: chose custom field definitions that apply only to the category they are attached to, with no inheritance from parent categories, because the WP specifies per-category fields and inheritance would make required-field resolution depend on tree traversal at every write (2026-08-07)
- WP-1.9: chose one row per ticket/field value with a canonical string `value` column over a JSON blob because uniqueness, deletion when a category changes, and future reporting all need the value addressable by field id (2026-08-07)
- WP-1.9: chose to canonicalise submitted values by declared type (decimal invariant, `yyyy-MM-dd`, exact select option) at the API edge because storage must not keep locale-dependent or unlisted values (2026-08-07)
- WP-1.9: chose a maximum category nesting depth of 3 with explicit cycle detection on reparent because deeper trees are unusable in a single-select picker and cycles would make the tree query non-terminating (2026-08-07)
- WP-1.9: chose to leave SLA policy matching on its existing free-text `Category` string and priority-only lookup because rewiring SLA to the new category tree is outside this WP's text (2026-08-07)
- WP-1.9: chose to keep the portal's Incident/ServiceRequest choice as a compact select in the details card rather than deriving ticket type from the category because no category→type mapping exists and requesters distinguish "broken" from "need something" usefully (2026-08-07)
- WP-1.9: chose to block deleting a category that has children or tickets (409) and to offer deactivation instead because ticket history must keep resolving its category name (2026-08-07)
- WP-1.9: chose to always refetch the category tree on mount (`staleTime: 0`) rather than share the 30s default because a cached tree can omit a field an admin has since made required, producing a 400 the form cannot attribute to any input (2026-08-07)
- WP-1.9: chose to keep the dev Postgres volume unnamed (fresh database whenever AppHost config changes) over pinning a stable volume name because the project wants a clean slate while testing; the consequence is that every fixture needed for manual verification must be seeded, not hand-created (2026-08-07)
- WP-1.9: chose to seed a required "Asset tag" custom field on the seeded "Laptop or desktop" category because a clean-slate database must still demonstrate a required per-category field without manual API setup (2026-08-07)
- WP-1.9: chose to seed a ten-node starter category tree in the demo seeder because a fresh Aspire environment must open the ticket forms with a usable picker, following the WP-1.7 seeded-queue precedent (2026-08-07)
- WP-1.10: chose database-generated `tsvector` columns (english) on `tickets(title, description)` and `ticket_comments(body)` with GIN indexes over query-time `to_tsvector` because only a stored column can be indexed, and generation keeps the vector in step with edits without trigger code (2026-08-07)
- WP-1.10: chose AND-ed prefix tsqueries (`auro:*`) built in application code over `websearch_to_tsquery` because the search box has to narrow results while an agent is still typing, and whole-lexeme matching only found the completed word (2026-08-07)
- WP-1.10: chose to strip tsquery operator characters from the typed term rather than escape them because the box is a search field, not a query language, and `to_tsquery` must never raise a parse error (2026-08-07)
- WP-1.10: chose to OR the ticket sequence number into the search predicate because agents paste "INC-000042" into the box and the number is a computed property that no text index covers (2026-08-07)
- WP-1.10: chose to search tickets and their comments in one query (ticket vector OR any matching comment vector), ranking by the ticket vector, because the WP requires a term inside an old comment to surface its ticket in the normal list (2026-08-07)
- WP-1.10: chose to exclude internal notes from requester searches while including them for agents because a requester must not learn that a private note exists (2026-08-07)
- WP-1.10: chose to add real server-side list filters (status, priority, type, queue, assignee/unassigned, category) to `/api/tickets` because a saved view is exactly a persisted filter set and the list previously accepted only pagination (2026-08-07)
- WP-1.10: chose to persist a saved view's filter as one `jsonb` column holding the same DTO the list endpoint accepts, over a column per filter member, because the two must not drift and new filters must not need a migration (2026-08-07)
- WP-1.10: chose shared views visible to every agent but editable and deletable only by their owner (403 otherwise) because users have no team membership anywhere in the model to scope sharing by (2026-08-07)
- WP-1.10: chose to enforce the agent-only surfaces (views, canned responses) inside the services with 403 ProblemDetails rather than adding an authorization policy because `CanManageTickets` deliberately includes EndUser and auth configuration is outside this WP (2026-08-07)
- WP-1.10: chose a fixed canned-response placeholder allowlist (`ticket.id`, `ticket.number`, `ticket.title`, `requester.name`, `agent.name`) with unknown tokens left literal because a silent empty substitution would ship a broken reply to a customer (2026-08-07)
- WP-1.10: chose to render canned responses server-side against the ticket rather than substituting in the browser because the requester display name is a Helpdesk snapshot and the same rendering will be reused by future automation (2026-08-07)
- WP-1.10: chose to have a canned response replace the previously inserted one only while the reply box still ends with it, appending once the agent has edited or typed past it, because cycling through templates must not leave stacked copies but hand-written text must never be destroyed (2026-08-07)
- WP-1.10: chose to seed three canned responses and one shared view because the dev database is recreated on most AppHost restarts and both features need a fixture to be verifiable by hand (2026-08-07)
- WP-1.11: chose a separate `HelpdeskHistorySeeder` over extending `HelpdeskDemoDataSeeder` because reference data and generated history have different result shapes, and the reference seeder must stay readable as the list of fixtures it is (2026-08-07)
- WP-1.11: chose to seed a business-hours calendar and four priority-only SLA policies, which were previously API-created only, because "SLA breach examples exist" is unreachable in a clean-slate database without a policy for `SlaService.StartAsync` to match (2026-08-07)
- WP-1.11: chose to write `TicketSla` rows with elapsed business seconds and warning/breach flags already consistent with each other, over letting `SlaEvaluationJob` discover the breaches, because the job would otherwise re-escalate and reassign every seeded ticket and emit a notification per row on its first pass (2026-08-07)
- WP-1.11: chose a fixed random seed plus ids derived from (kind, ticket index, child index), with every random draw taken before the already-exists check, because a re-run must add nothing and a partially seeded database must continue producing the same dataset (2026-08-07)
- WP-1.11: chose transition history that follows the linear WP-1.2 chain (New→Triage→InProgress→Pending→Resolved→Closed) because that is the only path the seeded `ticket_status_transitions` table permits, so any other history would be one no agent could have produced (2026-08-07)
- WP-1.11: chose usernames (`enduser1`, `technician1`) as seeded requester and assignee ids, following the WP-1.7 seeded queue, over inventing identity subjects because Keycloak assigns a random `sub` per environment; the consequence is that seeded tickets fill the agent lists but not a real requester's portal (2026-08-07)
- WP-1.11: chose to seed 200 tickets over three months of ages weighted by status (New within days, Closed up to five months old) because a flat age spread makes every list look artificially uniform (2026-08-07)
- WP-2.1: chose table-per-hierarchy for CIs with typed per-type columns plus a separate definition/value pair of tables for user-defined fields, over a flat table of config-driven fields, because "type-specific fields enforced" must be real validation and the attributes must stay queryable and indexable (2026-08-07)
- WP-2.1: chose `CiTypeSchema` as the one description of each type's fixed attributes — driving write validation, read projection and the form's field list — because TPH makes every per-type column physically nullable, so enforcement has to live above the database (2026-08-07)
- WP-2.1: chose explicit column names for the properties two sibling types share (`server_hostname`/`virtual_hostname`, `server_ram_gb`/`virtual_ram_gb`, `network_vendor`/`software_vendor`) because EF's TPH uniquifier would otherwise emit a meaningless `hostname1` column (2026-08-07)
- WP-2.1: chose to reject attributes belonging to another CI type rather than ignore them because a client posting the wrong shape must fail loudly instead of silently dropping data (2026-08-07)
- WP-2.1: chose a new `CanManageAssets` policy (Admin/Technician/Manager) over reusing `CanManageTickets` because the latter deliberately includes EndUser for the portal, and the CMDB is an agent-only surface (2026-08-07)
- WP-2.1: chose filtered unique indexes on `asset_tag` and `serial_number` because they are the WP-2.5 import dedupe keys, and most CIs will have neither (2026-08-07)
- WP-2.1: chose to reject a custom field whose key collides with a built-in attribute of the same CI type (409) because two fields with one key would make the submitted-value dictionary ambiguous (2026-08-07)
- WP-2.1: chose to drop a CI custom-field value when the field is absent from an update payload, mirroring the create path, because clearing an optional field in the form must clear it in storage (2026-08-07)
- WP-2.1: chose to canonicalise `managementIp` through `IPAddress.Parse` and mirror the octet check in the browser because a loose regex lets "10.0.0.999" reach the API as a 400 the form cannot attribute to a field (2026-08-07)
- WP-2.2: chose to persist the lifecycle graph as an `assets.ci_lifecycle_transitions` table seeded by the migration, following the WP-1.2 ticket-status precedent, because the guard is then data an operator can read rather than a compiled-in switch (2026-08-07)
- WP-2.2: chose a lifecycle graph of the forward chain plus the real returns (Deployed→InStock, InRepair→Deployed/InStock, InStock→InRepair/Retired) and no shortcuts, so Ordered→Disposed is a 409 while a repaired laptop can go back out (2026-08-07)
- WP-2.2: chose to restrict a newly created CI to Ordered or InStock (400 otherwise) because every later state must be reached through a guarded transition or the history would have gaps no agent could have produced (2026-08-07)
- WP-2.2: chose to freeze a Disposed CI — no edits, no assignment, no outbound transitions (409 each) — and to clear IsActive on disposal, because a disposed record states what the asset was when it left the estate (2026-08-07)
- WP-2.2: chose to check a CI back in automatically when it is retired or disposed, writing the CheckIn row into the log, because a retired asset nobody holds must not keep a stale owner on the record (2026-08-07)
- WP-2.2: chose a new Platform `IDirectoryService` (users, departments, sites) with agent-only `/api/directory/*` endpoints over letting Assets read `platform.user_profiles`, because a module may never query another module's tables (2026-08-07)
- WP-2.2: chose to store owner/department/site ids on the CI with name snapshots beside them, following the WP-1.7 requester-snapshot precedent, because cross-schema joins are forbidden and the check-in/out log must stay readable after a person leaves the directory (2026-08-07)
- WP-2.2: chose "location" to mean an existing Platform site rather than a new Assets location entity because sites are already seeded and modelled, and a second location table would need reconciling with them (2026-08-07)
- WP-2.2: chose `PUT /api/cis/{id}/assignment` to be a complete statement of ownership — omitting the owner checks the CI in — because a partial-update assignment endpoint gives no way to express "nobody holds this any more" (2026-08-07)
- WP-2.2: chose to derive the assignment log's action (CheckOut/CheckIn/Transfer/Relocate) in the service from the before/after owner rather than have the client name it, because the client could then mislabel its own history (2026-08-07)
- WP-2.2: chose to serve the legal next states from `/api/ci-lifecycle-states` and render only those buttons, over duplicating the graph in the browser, because two copies of a guard drift (2026-08-07)
- WP-2.2: chose a right-side drawer per DESIGN.md §6 for lifecycle and ownership rather than a CI detail page because the asset 360° page is WP-2.4's scope (2026-08-07)
- WP-2.2: chose to prefill the department and site from the selected owner's profile in the drawer, both still editable, because assets usually follow their holder but a machine can sit at a site its owner does not work from (2026-08-07)
