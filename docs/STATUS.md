- **⚠️ Correlation runs inline in the alert engine, and that was forced by how a poller batches.** WP-3.3 publishes **one `DeviceTelemetryReported` per cycle carrying every device the poller polled**, so a switch and its dependents cross their 3-cycle sustain count in the *same message* — at the top of that batch no alert row exists for any of them. - **⚠️ `AlertEngine.EvaluateAsync` is now three passes and the ordering between them is load-bearing.** Pass one advances every rule as though nothing were correlated and **writes nothing** — not the alert rows, not Redis; pass two works out what explains what; pass three re-advances the explained rules *from the state they started in*, suppressed. **The alert id is minted in pass one and carried**, so a re-advance produces the same alert rather than a second one. **The in-batch `working` state overlay is what replaced Redis's old job** of carrying state between two readings of one rule in one batch — a poller that fell behind sends several cycles at once, and without the overlay every one of them would read the same starting state and no "for N cycles" counter would ever advance.

- **⚠️ Suppression is never applied to a rule that has already been published, and that rule is not cosmetic.** WP-3.5 rebuilds "was anybody told about this" from the alert row's `Suppression` when Redis has forgotten (`LoadStateAsync`). Marking an already-published alert as suppressed would make it read as never-published, and **a Redis flush would then re-raise it — a second ticket for a problem that already has one**. - **⚠️ The engine's open-alert query is now estate-wide, where it used to be scoped to the batch's devices.** It has to be — a cause and its consequences are on different devices and are routinely polled on different cycles by different pollers. Bounded by how much is broken rather than by the size of the estate, and an alert row exists only while something is wrong, but **it is the first query in this module whose cost grows with the size of an outage**.

- **⚠️ The one thing correlation will never do is stay silent when it cannot name a cause.** Two mutually dependent CIs failing together explain each other, so neither is a root, so **neither is suppressed and both get tickets** — and a CI hanging off such a cycle publishes too. - **A scan reports a host that filters ICMP, and that is why the port fingerprint runs against every address rather than only the ones that pinged.** With no ports on the profile the step is skipped entirely and only ping-answering addresses exist as far as that scan is concerned — an ICMP-only sweep is the cheapest useful scan and stays cheap. **With ports, the cost is `addresses × ports` connects**: a /24 with six ports is 1,524 probes, which the 256-way concurrency bound turns into about a dozen seconds.

- **⚠️ `ScanRange` (C#) and `ranges.py` (Python) mirror each other by hand, and nothing cross-checks them automatically.** The same standing hazard WP-3.8 recorded for check parameters, in a new place. Both accept `local`, a CIDR, a span and a single address; both omit the network and broadcast addresses of anything wider than a /31, so the API's `addressCount` and the scanner's actual probe list agree. **Both suites assert the same counts for the same strings** (`ScanProfileRulesTests.Range_EveryAcceptedForm_CountsTheAddressesItProbes` and `test_ranges.py`), so a drift shows up as one of them failing rather than as a range nobody scans. The API validates and counts but **never enumerates** — a `/8` posted to an endpoint that materialised addresses would be sixteen million strings inside a web request.

- **The discovery service has no heartbeat and no registration, which is a deliberate departure from WP-3.2's poller.** A scanner with nothing new to report is indistinguishable from an estate with nothing new on it, so "missed N heartbeats" would fire on the normal case. **Consequence: a crashed scanner is silent** — nothing on any dashboard says so, and the only symptom is a review queue that stops filling. - **pysnmp is wrapped in `asyncio.to_thread` here and is not in the poller, which is the WP-3.8 defect being avoided rather than fixed.** WP-3.8's walk measured one SNMP check stalling the event loop for 35-81 ms doing its BER/ASN.1 work synchronously. A poller runs a handful of checks a cycle and merely mis-measures its own latency; a scan identifies **every** address that answered, so the same stall would serialise the whole thing behind the parsing. **The poller's own fix is still outstanding** — see the WP-3.3 note below — and this service is now the worked example of what it should look like.

- **Profiles are scanned one at a time, sequentially, inside a cycle.** Each is already hundreds of probes in flight; two together would double that against a network whose capacity this service knows nothing about, and the concurrency bound would stop meaning anything. **Consequence: a slow profile delays the ones behind it**, and the scheduler marks a profile run when it starts rather than when it finishes, so a scan that overruns its own interval is not started twice.

- **⚠️ Two more things a scan cannot do, both deliberate and both worth knowing before somebody promises them.** (1) **SNMP v3 is not attempted at all** — a scan tries a list of community strings against a stranger, and USM needs a user, a protocol and a key *per device*, which only exists once the device is known. A v3-only device is discovered by its ping and its ports with no identity, and gets one in WP-4.2 when somebody attaches a credential. (2) **No MAC address is collected.** WP-4.2's text names MAC as a matching heuristic; an IP sweep from another subnet cannot see one (ARP is link-local), and the ARP-table route is a walk of `ipNetToMediaPhysAddress` on a *router* rather than a property of the scanned host. **WP-4.2 has serial, IP and hostname to match on, and should plan for that.**

- **🔐 The vault is `platform.credentials`, and the material is write-only in a way that is worth restating.** No endpoint returns a secret: not the create response, not the list, not the audit entry, not the stored row (it is Data Protection ciphertext). The **one** method in the repository that decrypts is `CredentialVault.RedeemGrantAsync`, the **one** type that carries plaintext is `ReleasedCredential`, and the **one** route out is `POST /api/credential-grants/redemptions` behind `CanPoll`. `Credential_Created_NeverReturnsItsSecretAndStoresItAsCiphertext` checks all four surfaces for the literal string and fails if any of them starts carrying it.

- **⚠️ The Data Protection key ring lives in `platform.data_protection_keys` and losing it means losing every credential.** The framework default is a key ring under the host's own directory, which in a container means a fresh key on every restart and every stored secret silently undecryptable — nothing fails until something tries to poll. It is now persisted beside the ciphertext, namespaced by `SetApplicationName("it-platform")`, which **the Seeder console app has to configure identically** — it builds a small DI container for exactly that reason, and a default provider there would encrypt the seeded communities with a key it throws away on exit. **The ring is stored unencrypted**: on one host the key and the ciphertext are equally readable to anybody with the database, and protecting it properly wants a KMS or an HSM. That is a deployment gap, recorded in DECISIONS.md, and it is the honest state of "encrypted at rest" here.

- **A rotation is a version number, and that is the whole propagation mechanism.** `POST /api/credentials/{id}/rotations` replaces the secret and increments `Version`. The poller reads `GET /api/pollers/{name}/credentials` every cycle — metadata only, no material, **no row written** — and asks for a grant only when a version it holds has moved. So "rotate → the poller picks it up next cycle" is literally true, and a steady state costs one cheap GET per cycle rather than an audited secret release. **Nothing pushes**: Platform may not write to a monitoring table, so there is no way to bump the config version from a rotation.

- **A grant is single-use, expires in 120 seconds (`Platform:Vault:GrantLifetimeSeconds`), and its token is stored only as a SHA-256 hash.** Redemption looks the grant up **by hash** and then checks the id in the request against what it found — so an unknown grant, a wrong token and a mismatched pair are all the same 404, deliberately, because distinguishing them makes the endpoint an oracle. **Expired grants are swept on every issue**, which bounds `platform.credential_grants` to the lifetime window; that is the opposite call to WP-3.10's `notification_deliveries` and is only right because a grant is a permission slip nobody reads afterwards.

- **The poller never names a credential in any request.** Its scope is derived by Monitoring from the enabled checks on enabled devices in its own poller group (`PollerCredentialService`), so there is no request a poller can make that widens what it may read. **Consequence: disabling a device or a check removes its credential from that poller's scope on the next cycle, and `CredentialStore.retain` drops the material out of the process** — which makes disabling an effective way to stop handing a secret out.

- **⚠️ `CanPoll` is disjoint from every operator policy, and this cuts both ways.** Managing credentials is `AdminOnly` — a Technician who can edit a check must not be able to replace the secret it authenticates with — while **redemption is the `Poller` realm role and not Admin**, so there is no operator-facing path to material anywhere in the platform. Verifying the redemption endpoint by hand therefore needs a poller token (`client_credentials` against `it-platform-poller`; secret via `dotnet user-secrets list --project src/AppHost | grep poller-client-secret`), exactly as WP-3.2 recorded for the config fetch.

- **⚠️ A poller's identity is still not checked against the poller name in the URL.** `CanPoll` says "some poller"; it does not say "this poller". So a poller token can fetch another poller's scope and mint a grant over another group's credentials. This is **pre-existing** — `GET /api/pollers/{name}/config` has had the same shape since WP-3.2 — but it matters more now that the same shape reaches secrets. **The fix is to bind the token's client id to the poller row**, which is a change to WP-3.2's registration and is nobody's WP. - **The poller merges material over a check's parameters at the moment the check runs, not into its cached configuration.** `CredentialStore.apply` returns a `DueCheck` with `{**parameters, **material}` — **the vault wins on a collision**, which is what makes a rotation take effect over a stale plaintext copy. That is correct — a clear is Informational so a "Critical only" pager does not become the all-clear — but the seeded rule set has minimums of Warning and Critical, so *nothing* carries an all-clear. **Anyone who wants recovery messages needs a rule at Informational.** `platform.consumer_dedupe_entries` shows `alert-notification-cleared` ran; the router simply matched no rule.

- **⚠️ A preference is keyed by the actor's Keycloak `sub`, and an SLA notification addresses the ticket's assignee id. Those are different keys.** The live walk saved a preference for `technician1` and it stored under `58296981-…` (the `sub`), while WP-1.11's seeded tickets carry `technician1` as the assignee. **So a preference saved in the browser does not apply to a seeded ticket's notifications.** This is the WP-1.11 identity mismatch again, and it is why the *routing effect* of a preference was verified by integration test rather than live — no SLA event fires on the seeded estate without hand-editing SLA rows (the seeded flags are pre-set precisely so the job will not re-fire).

- **⚠️ Two things the walk could not prove.** (1) **The deep link was never clicked in a real browser**: headless Chromium here is missing `libnspr4`, and installing system packages is a machine change. The URL is correct, `GET /api/alerts/{id}` for it returns the alert with five open tickets, and the drawer has four vitest tests including the `?alertId=` case — but nobody has seen it open. (2) **Step 4 was captured against a local HTTP sink, not a real Teams tenant.** What is proven is the exact JSON on the wire (MessageCard, `themeColor` `D93025`, `potentialAction` OpenUri, the WP-3.7 facts); that Teams *renders* it is not.

- **A local webhook sink is the cheapest way to re-walk step 4, and `PostAsJsonAsync` sends chunked.** Nothing in the dev stack receives an HTTP webhook (MailHog is SMTP with an HTTP UI). A ~30-line `http.server` script works — **but it must decode `Transfer-Encoding: chunked`**, because `HttpClient` streams JSON without a `Content-Length`; a sink that reads only `Content-Length` logs empty bodies and looks like the platform posted nothing. That cost ten minutes of this walk.

- **⚠️ The seeded estate alerts on its own within a minute of a fresh `aspire run`, which makes steps 4 and 5 free.** The degraded snmpsim profile raises CPU Critical and Memory Warning, and `192.0.2.1` is unreachable by design — so a fresh run produces a Critical *and* a Warning with no intervention, and `GET /api/notification-deliveries` shows the Critical reaching Email+Teams and the Warning reaching Email only. Nothing has to be stopped to see the WP's two routing cases.


- **`Notifications:Seed:WebhookUrl` is the one switch that seeds the chat half.** Unset (the default) seeds the email channel `IT Operations email` plus the rule *Warning and above to email*, and no chat channel at all — a placeholder webhook would fail every Critical alert and read as a broken feature. Set it (with `Notifications:Seed:WebhookKind` = `Teams` or `Slack`) and the seeder adds `IT Operations chat` and *Critical to chat*, which is the WP's two-rule verification case. AppHost passes both through to the seeder; a re-run refreshes the URL on the existing channel and leaves everything else, including a hand-made deactivation, alone.

- **⚠️ SLA notifications no longer go straight to SMTP, and an unresolvable assignee is now a recorded suppression rather than silence.** `SlaService` calls `INotificationRouter` instead of `INotificationService`, so a warning, a breach (new — a breach notified nobody before) and an escalation each produce a `notification_deliveries` row. The recipient is the ticket's assignee, or the requester when unassigned, and their id is resolved against `platform.user_profiles` by username or directory id. **Seeded helpdesk identities are usernames (WP-1.11) and do resolve; a Keycloak `sub` from a browser login does not**, and that case now reads `No email address is recorded for this recipient` in the delivery row instead of being dropped by `SmtpNotificationService` with a log line. `TicketApiIntegrationTests.SlaClock_…` had to be narrowed to assert the delivery rows rather than the old template names — the same class of change WP-3.4 made to a WP-0.5 test.

- **Alerts reach channels only; they never address a person.** `ICiDirectory` answers with an owner's *name* rather than an id (WP-2.4), so there is nobody on an alert to apply a per-user preference to. **Per-user preferences therefore govern the SLA path alone today.** Widening `CiSummary` with an owner id is the change that would fix it, and it is nobody's WP.

- **Routing rules are additive and deduped by channel, not ordered.** Every active rule whose event kind, minimum severity and device group the envelope satisfies fires. Where two rules select one channel the collision resolves toward the operator hearing about it — a rule that would send beats one inside quiet hours, and one that digests beats one that drops. **A rule that names a device group deliberately does not match an envelope with no group**, so a network-team rule is not woken by an SLA breach.

- **⚠️ Severity is stored as its name, so a minimum-severity filter cannot be a `WHERE` clause.** `NotificationRouter.MatchRulesAsync` loads the active rules and filters them in memory for exactly the reason WP-3.9 recorded for the alert board's sort: `>= 'Warning'` in SQL compares spellings. There are a handful of rules; a "simplification" that pushes the comparison into the database silently reorders the severity scale.

- **A webhook URL is treated as vault material a package early.** It is stored in `platform.notification_channels.target` in clear (WP-3.11 owns encryption at rest) but **no read ever returns it**: responses and the audit entry carry `NotificationChannel.Redact` output only, and `PUT` with a null `target` means "leave it alone" — which is what makes editing a channel possible without the client knowing a value no read has given it. `Channel_Created_NeverReturnsItsWebhookUrl` fails if that changes.

- **⚠️ `platform.notification_deliveries` is both the durable record and the digest queue, and it is never pruned.** A withheld notification is a `Deferred` row carrying `release_after`; the digest pass turns a group into one `Sent` row and marks each contributor `Digested`. **Nothing deletes any of these rows** — one per notification per destination, forever. A retention policy is the obvious next thing and no WP owns it.

- **The digest pass is at-least-once on purpose.** Contributors are marked `Digested` in the same `SaveChanges` as the digest row, *after* the send — so a crash mid-pass leaves them `Deferred` and the next pass retries. A duplicate digest beats a silent hole. It runs on Quartz every `Notifications:DigestIntervalSeconds` (default 300), so a 07:00 digest lands somewhere in 07:00–07:05, and `POST /api/notification-digests/runs` triggers the same pass by hand (the WP-2.6 reason: the dev database is recreated on most AppHost restarts).

- **Quiet hours need both ends or neither, and are evaluated in their own IANA zone.** A window that wraps midnight is the case the comparison is written for. **A time zone that is refused at write time falls back to UTC at evaluation time** — a typo must not throw on the alerting path. `QuietHoursSchedule` is pure and is where all of this is tested.

- **A quiet-hours rule that does not digest *drops* the message**, and the delivery row says `Suppressed: Inside quiet hours, which do not digest.` That is a lossy setting somebody chose; the row is the only evidence it happened.

- **The alert board now has a detail drawer, opened from `?alertId=` (`AlertDetailDrawer.tsx`).** It is the first caller of `GET /api/alerts/{id}`, which WP-3.7 built and WP-3.9 left unused, and it is where a chat deep link lands. Clicking an alert's summary opens the same drawer. **The drawer is the only place open related tickets are shown** — they cost a query per CI and are still deliberately absent from the board's rows.

- **`Notifications:DeepLinkBaseUrl` is set by AppHost from `public-host`, the same value as the QR-label base URL.** Unset, notifications carry **no link at all** rather than a relative one: a relative URL in a chat client goes nowhere. So a link printed into Teams is only as good as `public-host` was when the alert fired.

- **A webhook is a third party on the alerting path and is bounded at 10 seconds** (`WebhookNotificationChannel.Timeout`). Every channel swallows its own failures and returns a result the router records — a broken hook must not be able to fail the alert raise that caused it, which is the WP-3.9 SignalR rule. The consequence is that **a dead webhook is visible only as `Failed` rows and a log line**, never as a missing alert.

- **Two consumers were added to Monitoring for events Monitoring itself publishes** (`AlertRaisedNotificationConsumer`, `AlertClearedNotificationConsumer`), on their own endpoints beside Helpdesk's ticket automation. That is deliberate: a Teams webhook that will not answer must not stop a ticket being opened. Both use the Platform dedupe helper — a redelivery would otherwise post the same alert into the same channel twice, and a notification cannot be un-sent.

- **FluentValidation is now referenced by `Platform`** (12.0.0, the version all three modules already use). It is the first validation dependency outside the modules and exists because Platform now owns an API surface of its own.

- **⚠️ A `Guid.CreateVersion7()` prefix is not unique, and it cost two rounds of debugging in this package's tests.** A v7 GUID opens with the 48-bit millisecond timestamp, so `Guid.CreateVersion7().ToString("N")[..8]` is **identical for every GUID created inside the same ~65 seconds** — which made a "unique per test" suffix the same for every test in the run, colliding on the unique name indexes and cross-matching every routing rule. Use `Guid.NewGuid()` for a short random suffix. Nothing else in the repo does this today; if a future test wants one, this is the note.

- **⚠️ Another shared-table trap, and a new shape of it: routing rules are global, so one test's channel receives every other test's notifications.** `NotificationRoutingIntegrationTests` scopes every rule it writes to an event kind only that test publishes. The symptom is a count that grows with the suite, and it passed alone. Related: **a channel's *name* is returned by every read**, so a test that named a channel after its target leaked the string a redaction assertion in another file was scanning for — do not put a target in a name.

- **⚠️ WP-3.9's manual checklist has not been walked.** Everything below is what the code does and what the automated tests assert; nothing here has been seen on a live `aspire run`. The two steps most likely to surprise are in the next note.

- **⚠️ "Both boards update <1s" is about the *push*, not about noticing a device is down.** Stopping a device does not raise an alert for `SustainedCycles × interval` — on the seeded estate that is 3 × 15s, so **expect ~45s before anything appears**, and then both browsers inside a second. The WP text's "stop a device → both boards update <1s" is only achievable read that way, the same way WP-3.2's "within 2 cycles" was not literally reachable. The checklist says so explicitly; do not treat the 45s as a fault.

- **A SignalR push does not go through the outbox, and that is the one deliberate departure in this package.** `AlertEngine.PublishAsync` and the acknowledge endpoint both call `IMonitoringLiveUpdateService` directly, after the alert row is committed. The reasoning is that a push is a *projection* of committed state rather than a fact — nothing downstream consumes it, and the SPA re-reads every board on reconnect (`onResync`), so a missed push is self-healing. **Consequence: a browser can see an alert before WP-3.6's ticket for it exists**, because the ticket comes off the bus and the board does not. That is correct and visible in the demo.

- **The broadcast is swallowed on failure, so a broken hub cannot fail a raise.** `MonitoringLiveUpdateService` catches everything except cancellation and logs one line. **Consequence: the only symptom of a dead backplane is stale boards plus that log line** — the "Live"/"Reconnecting" indicator in each board's header is the operator-facing half, and it is the only thing that distinguishes a quiet estate from a board that stopped receiving.

- **Acknowledgement is an annotation and suppresses nothing.** It does not reach WP-3.5's state machine, does not change severity or a tile's colour, and does not travel to WP-3.6's automation — an acknowledged Critical still shows Critical everywhere. It also **does not survive a clear**: a recurrence opens a new alert row, so the same problem coming back is unacknowledged again. Acknowledging twice, or acknowledging a cleared alert, is a **409 naming who holds it** rather than a silent overwrite.

- **⚠️ A disabled device's open alerts can never clear, and the tile now shows that.** Disabling a device removes it from every poller's configuration, so no telemetry arrives, so WP-3.5 never evaluates its rules — its open alerts sit open forever. The tile reads `Disabled` while still carrying the stale counts. **Nothing closes them today**; if that is ever wanted it is a change to the device-disable path in WP-3.1's service, not to the board.

- **`DeviceStatus.Unknown` means "enabled and has never reported", and it is derived from the metrics hypertable over a two-day lookback.** A device silent for longer than two days reads the same as one that has never reported — same tile, same conclusion. The window is bounded so the query prunes chunks instead of scanning the retention period.

- **There is still no device-level roll-up of alerts into one incident.** A dead switch with four checks shows four open alerts and one red tile; the tile is the roll-up, the alert board is not. **WP-5.1 root-cause suppression owns that**, which is unchanged from what WP-3.5 recorded.

- **The alert board's rows carry the CI half of WP-3.7's context; only the alert *detail* endpoint carries open related tickets.** `ICiDirectory` takes a list of ids and answers a page in one query; `ITicketLinkDirectory.GetOpenTicketsForCiAsync` answers one CI at a time, so putting tickets on the list would be a query per row on every refresh. **`GET /api/alerts/{id}` is therefore the expensive one** and the SPA does not call it yet — the board renders entirely from the list. It exists because WP-3.7's "shown on alert board" half asked for it and a future drawer is its caller.

- **⚠️ The alerts API's test host had to migrate `HelpdeskDbContext`, which is the WP-3.6 port trap again.** `GET /api/alerts/{id}` reads Helpdesk through `ITicketLinkDirectory`, so a host that never migrated the helpdesk schema answers **500**, not a DI failure. Four tests failed exactly that way before the migrate was added. **Any host that reads another module through a port needs that module's schema**, and this is the third package to learn it.

- **Severity is ordered by two boolean sort keys, not by the column.** `AlertSeverity` is stored as its name, so `ORDER BY severity` sorts Critical, Ok, Warning alphabetically and buries the warnings under the recoveries. `AlertService.Ordered` is where that lives; a rewrite that "simplifies" it to a plain `OrderByDescending(alert => alert.Severity)` silently reorders the board and no test outside `Alerts_Listed_AreOrderedWorstFirstThenNewest` would notice.

- **Two new frontend dependencies, both named by binding documents rather than chosen here:** `recharts` (DESIGN.md §2 names it as the chart library) and `@microsoft/signalr` (the WP text and ARCHITECTURE §4). Recharts is **lazy-loaded behind the device page alone** — it is 381 kB of the build, and splitting it keeps the main bundle at 856 kB rather than 1.24 MB. Nothing else in the SPA may import it eagerly without undoing that.

- **The hub has no client-callable methods and never will without a reason.** Acknowledging is the HTTP endpoint, which validates, authorizes and audits; a hub method would be a second write path around all three. The socket is one-way by design.

- **The JWT bearer handler now accepts a token from the `access_token` query string, for `/hubs` paths only.** A browser cannot set an Authorization header on a WebSocket handshake. It is deliberately scoped to those paths — a token in a URL is a token in an access log, and widening this is a credential leak on every other endpoint. CORS also gained `AllowCredentials()`, which is safe only because the origin is a single configured value.

- **A monitored device now has a page in the SPA (`/monitoring/devices/{id}`) but there is still no way to create, edit or delete a device or a check in the browser.** WP-3.1's API is complete and reachable only from a REST client; this package built the read side. The device page's chart picker, range picker and threshold lines are all driven from those endpoints. **Whoever wants a monitoring admin screen should know it is nobody's WP yet.**

- **🐞 A defect found by WP-3.8's own hand-verification and deliberately NOT fixed: `check.latency_ms` on a TCP or HTTP check is wall-clock time across an event loop that pysnmp blocks, so it measures how busy the poller was rather than how fast the service answered.** On the live estate the same MailHog TCP connect reported **181 ms** on a cycle shared with the SNMP checks and **2.7 ms** on a cycle without them; an isolated connect from inside the poller container is 0.4–0.6 ms, and DNS is not the cause (`getaddrinfo` measured at 0.16–3.4 ms). Measured directly: **one SNMP check stalls the loop for 35–81 ms in a single go** — `snmp sysinfo` 81.49 ms, `snmp memory` 35.58 ms, against 2.25 ms for a TCP check — because `pysnmp_transport.py` does its BER/ASN.1 work synchronously on the loop. **This matters because `AlertRules.PrimaryMetric` maps Tcp and Http to `check.latency_ms`, so a latency threshold on a service check today alerts on poller busyness.** The availability rule is unaffected, which is why every step of the checklist still passed. **The fix is in WP-3.3 code** — wrap the pysnmp calls in `asyncio.to_thread` (or give SNMP its own executor) — so it wants a `fix/` branch with a loop-stall test, exactly like the WP-3.1 and WP-3.5 defects below. Until then, **set thresholds on TCP/HTTP checks only for gross latency (seconds), never tens of milliseconds.**

- **⚠️ A checklist-ordering trap, not a defect: run the content-match step and the kill-the-container step at least 10 minutes apart.** The WP-3.8 walk drove the HTTP check through four state changes inside the 600 s flap window (content expectation broken → restored → container stopped → container back), which trips WP-3.5's flap threshold of 4. The clear was therefore withheld and the alert sat Open at severity `Ok` for a further ten minutes — `flappingUntil` in the Redis state read `01:53:38`, exactly 600 s after the recovery that tripped it, and the alert cleared on the first reading after that. The TCP check next to it, with only three flips in the window, cleared in 37 s. **Both rows read `is_flapping = false` and `suppression = None` afterwards, because the row records the final reconciled state rather than the history — the evidence is only in Redis**, which is worth knowing before anyone chases this as a stuck alert.

- **An alert summary no longer double-punctuates its reason, and the seeded mail device names the mail service.** Two fixes made after the walk, both verified on a second live run. (1) `AlertRules.EndSentence` terminates the availability summary exactly once — the poller writes whole sentences, so appending a full stop unconditionally produced "…after 3 packets.." on **every** failing check in the estate since WP-3.5; a `like '%..%'` scan over the alert table now returns nothing. (2) The fourth seeded device is picked by **name** (`assetsResult.CiIds["svc-mail"]` → *Corporate Email Service*) rather than `ServiceCiIds.Take(1)`, which was *Finance Reporting Service* and made every screen say a mail outage was a reporting outage. The named lookup also survives an estate reordering, which the positional one did not; it falls back to the old pick if the key is ever renamed, so the device is never lost.

- **The poller now runs five kinds of check, and the seeded estate has four devices rather than three.** `services/poller/src/poller/checks/{tcp,http,tls}.py` join ICMP and SNMP, wired in `__main__.py`. The fourth seeded device hangs off a **service** CI (`assetsResult.ServiceCiIds.Take(1)`, appended after the three network ones — the first three stay first because WP-3.7 gave exactly those an owner) at address `mailhog`, carrying a TCP check on 1025 and an HTTP check on the UI. It deliberately has **no ICMP check**, so WP-3.3's "any check that completed decides reachability" fallback is finally exercised by the seeded estate. AppHost passes MailHog's name and ports to the seeder the same way it passes snmpsim's, and the poller now `WaitFor`s MailHog.

- **⚠️ The TLS check does not verify the certificate it measures, and that is the point.** `CERT_NONE` plus `getpeercert(binary_form=True)`: a verified handshake returns a parsed certificate but *fails* on a self-signed or already-expired one, which is exactly the certificate somebody wants a countdown for — the check would flip from "expires in 3 days" to "the check is broken" on the day it mattered. **Consequence: this check never answers "is this certificate trusted".** Nothing in the platform does. If trust ever needs monitoring it is a second check type, not a flag on this one.

- **An expired certificate reports as a *successful* check with a negative `tls.days_to_expiry`.** Same rule as WP-3.3's 100% packet loss: a failed check advances the availability rule instead, and the days figure — the number the threshold is actually set on — would never reach the alert engine. So a TLS check's thresholds are `LessThan` with warning 30 and critical 7, and the alert fires off the number rather than off the check failing.

- **`cryptography` is the poller's fourth dependency and the first added since WP-3.3.** It exists solely to parse X.509 DER, because the standard library will not hand back a parsed certificate from an unverified handshake. CI already installs the poller with `pip install -e '.[dev]'`, so nothing else changed; the Dockerfile picks up a manylinux wheel with no toolchain.

- **No TLS check is seeded.** Nothing in the dev stack serves HTTPS, and a seeded check pointed at a public host would raise a permanent alert on a machine with no internet. The manual checklist creates one by hand — which means **the "cert check reports days" step needs outbound internet**.

- **⚠️ `AlertRules.PrimaryMetric` and `CheckRules` now mirror the poller by hand in three more places, and nothing cross-checks them.** `tls.days_to_expiry` must match `checks/tls.py`, and `expectedStatus`/`method`/`expectedContent` are validated by `CheckRules.HttpProblem` in C# and applied again by `checks/http.py` in Python. `expectedStatus` was deliberately kept to a **single status code** rather than a list or a `2xx` class for exactly this reason — every form the rule can take is a form the two languages can come to disagree about. The WP-3.2 envelope fixture is the pattern if this ever needs a real cross-language guard.

- **Two knobs deliberately not built on the HTTP check:** there is **no way to skip TLS verification** on an `https://` URL, so an internal service with a self-signed certificate cannot be checked with an HTTP check today (use a TCP check, or a TLS check for the certificate itself); and there is no request body, header or auth. Both are additions somebody will eventually want and neither is in this WP's text.

- **⚠️ `Seed_EveryCheck_PassesTheRulesItsOwnApiWouldApply` excludes SNMP checks on purpose.** It asserts every seeded check would survive `CheckRules.Validate` — the guard against seeding a check nobody can edit. SNMP is excluded because it *does* fail, which is the WP-3.1 `RequiredParameter[Snmp] = "oid"` defect recorded below, still unfixed. **Narrow that exclusion when the defect is fixed rather than leaving it.**

- **⚠️ `dotnet run --project src/Seeder` by hand needs the database named `it_platform`, with an underscore — and it almost never needs running at all.** AppHost already runs the seeder as a resource (`src/AppHost/Program.cs:234`), so a fresh `aspire run` is seeded by the time the API is up. Running it by hand with `Database=it-platform` (the hyphenated resource name) silently **creates a second, empty database** and reports a full successful seed against it, after which every hand-written SQL check reads zeros while the API is demonstrably working. That cost twenty minutes of this walk. Read the connection string off the API, not off the Aspire resource name.

- **⚠️ The RabbitMQ data volume outlives an `aspire run`, so a stale error queue is not this run's evidence.** This walk opened on `AlertTelemetry_error` holding 6 messages, all `23505 duplicate key … ix_alerts_device_id_rule_id` from `AlertTelemetryConsumer` — **all six dated 2026-08-10 23:18–23:21 with `MT-Fault-InputAddress` naming broker port 45695, i.e. a previous session's broker.** Always read `MT-Fault-Timestamp` and `MT-Fault-InputAddress` before believing a dead letter belongs to the run in front of you. (Those six are a WP-3.5 finding — the filtered unique index losing a race — and are nobody's scope yet.)

- **✅ WP-3.7's "shown on alert board" half is now built (WP-3.9).** The board calls `IAlertEnrichmentService` rather than re-deriving anything: `SummariseAsync` for a page (batched, CI fields only) and `DescribeAsync` for one alert (adds open related tickets). The alert's context remains observable in the `AlertRaised`/`AlertCleared` **audit entry** (`platform.audit_entries`, `after_json.cmdb`) and the engine's log line as well, and those two stay dated records of what monitoring saw while the board reads live.

- **The automated ticket now links its CI, which closes the WP-3.6 gap.** `AlertTicketAutomation` calls `ITicketCiLinkService.LinkAsync` under `system:monitoring` after the ticket is created, so the link is audited, publishes `TicketCiLinked`, and shows on the ticket's Linked-assets card *and* on the CI's ticket list (`/api/tickets?ciId=`). **A link that cannot be made never fails the raise** — a CI missing from the CMDB logs one line and the ticket still opens, with "not found in the CMDB" in its description instead of blank owner fields.

- **CMDB context is read live everywhere except two dated records.** `CiSummary` gained `DepartmentName`, `WarrantyExpiresAt`, `WarrantyStatus`, `WarrantyDaysRemaining` and `ContractName`; `ITicketLinkDirectory` gained `GetOpenTicketsForCiAsync`. Both are re-read on every request (WP-2.4's rule). The exceptions are deliberate: the automated ticket's **description** and the alert's **audit entry** are written once and never rewritten, because they state what monitoring saw at the time. **Consequence: a ticket's description and its asset card can disagree after a reassignment, and that is correct.**

- **Warranty status is computed by Assets, not by the reader.** `CiDirectory` runs `ContractExpiryCalculator`, so "expiring soon" is the same 30 days on a ticket card, in an alert's audit entry and in a WP-2.6 renewal notice. Anything else that ever needs a warranty status must come through this port rather than compare a date itself.

- **⚠️ Two test hosts now need modules they are not about.** `AlertTicketBusIntegrationTests` had to add `AddAssetsServices` + an `AssetsDbContext` migrate (the automation resolves `ICiDirectory`, which only Assets registers — without it the consumer could not be constructed and every `AlertRaised` faulted into `AlertRaised_error` with nothing in the logs to explain it), and `AlertEngineIntegrationTests` had to migrate `HelpdeskDbContext` (the engine asks Helpdesk for open tickets on every publication). **Any future host that constructs a consumer has to register every module that consumer reads through a port**, and the symptom of forgetting is an error queue rather than a DI exception at start-up.

- **The three seeded DC1 core network CIs are now held by `technician2`.** They were unowned, and `NetworkCiIds.Take(3)` — estate order, so `dc1-core-rtr-01`, `dc1-core-sw-01`, `dc1-core-sw-02` — is exactly what the monitoring seeder monitors, so the WP's "alert on seeded switch shows owner/location" had nothing to show. Their warranty is 640 days out (**`Active`**, deliberately unchanged so the WP-2.6 notice set does not move); the `ExpiringSoon` and `Expired` states are demonstrable on the seeded laptops. `SeedAsync_TheMonitoredNetworkCis_CarryTheContextAnAlertIsSupposedToShow` fails if a reordering of the estate moves the monitored three.

- **🐞 A WP-3.5 defect found by WP-3.6's hand-verification and deliberately NOT fixed here: with Redis down, the alert engine stops evaluating and holds telemetry unacknowledged.** `docker stop` on the Redis container, then twelve new breaching checks: `DeviceTelemetry` stayed at 0 (WP-3.4's ingestion is unaffected — the separate-queue decision working exactly as intended), while **`AlertTelemetry` climbed to 18 messages, 16 of them unacked**, no alert was raised for five minutes, and messages eventually dead-lettered into `AlertTelemetry_error`. `RedisAlertStateStore` catches `RedisException`, so this is not an unhandled throw — the calls **block** on StackExchange.Redis' reconnect/timeout behaviour, once per rule per cycle, until the consumer's prefetch is exhausted. **This contradicts the WP-3.5 note above** ("A Redis outage is logged and swallowed — an alert engine that stops evaluating because a cache is unavailable turns one outage into two"): it is swallowed, but not quickly enough to keep evaluating. The fix belongs in `RedisAlertStateStore` — an aggressive `ConnectTimeout`/`SyncTimeout` on the multiplexer, or a short circuit that skips the store while the connection is down. It wants a `fix/` branch. **Consequence for WP-3.6: no alert reaches the automation during a Redis outage at all**, so the guard's durable fallback cannot be observed from the live loop; `AlertAutomationGuardTests` proves it in process instead, against a multiplexer aimed at a closed port.

- **⚠️ Restarting an Aspire container by hand does not restore it.** `docker start` on the stopped Redis gave it a **new host port**, and the API holds the connection string Aspire injected at launch — so the API stayed `Unhealthy` and its Redis stayed unreachable for the rest of the run. Any "stop a dependency, start it again" verification step has to restart the whole `aspire run`, not the container. This is the same class of trap as WP-3.3's `host.docker.internal` finding.

- **🐞 A WP-3.1/WP-3.3 defect found by the same walk and NOT fixed: a seeded SNMP check cannot be edited through its own API.** `CheckRules.RequiredParameter[Snmp]` is `"oid"` (WP-3.1), written before WP-3.3 introduced the `metric` families — so the seeder's checks, which carry `metric=cpu`/`memory` and no `oid`, are refused with `400 A Snmp check requires a 'oid' parameter.` on any `PUT /api/checks/{id}`. They poll perfectly well; they simply cannot be changed. The fix is to require `oid` only when `metric` is absent or `oid`. Nothing tests editing a seeded check.

- **An alert becomes a ticket in Helpdesk, and the dedupe key is a durable row rather than a cache entry.** `helpdesk.alert_tickets` holds one row per `alert:{deviceId}:{ruleId}` with a **unique index** on it, so a second ticket for an open problem is refused by the database. A repeat raise becomes an **internal comment** on the ticket that already exists; an escalation says which way it went. `AlertRaisedConsumer`/`AlertClearedConsumer` live in `Modules.Helpdesk` (the module that reacts) and are handed to Platform's bus through `HelpdeskServiceCollectionExtensions.AddHelpdeskConsumers`, beside Monitoring's — **`Program.cs` now passes a lambda calling both**, which is the pattern for the next module with a consumer.

- **⚠️ "Auto-resolve" is four transitions, not one, and that is load-bearing.** The WP-1.2 status graph is the linear chain New→Triage→InProgress→Pending→Resolved→Closed, so the automation walks it hop by hop through `ITicketService.TransitionAsync` — the route is found breadth-first from `ticket_status_transitions` rather than hardcoded, so a shortcut added later is used. Consequences: an auto-resolved ticket's history shows all four hops under actor `system:monitoring`; **and there is no way to reopen**. A rule that recurs after its ticket was resolved or closed gets a **successor ticket**, with a note on each pointing at the other. If reopening is ever wanted it needs a new edge in the seeded graph, which changes the workflow for human agents too and is nobody's scope yet.

- **The bounds are a per-rule rate limit and a *global* circuit breaker, and the breaker has to be global.** Fifty distinct alerts each pass their own per-rule limit — that is precisely the storm. Defaults live in `Helpdesk:AlertTickets` (rate 3/min per rule, breaker 10 tickets per 60s, cooldown 300s, admin `it-admin@it-platform.local`). Redis holds both counters (`helpdesk:alert-ticket:*`, ARCHITECTURE §5); **the breaker falls back to counting `alert_tickets` rows in the window when Redis is unreadable, the rate limit does not** — a bound that vanishes with the cache is not a bound, while a per-rule ticket is already capped at one by the durable row. The breaker **drops its window when it trips**, or it would still be over threshold when the cooldown expires and would never close. The admin is notified **once per trip**, claimed with a SETNX.

- **A sustained alert adds nothing to its ticket, and the checklist's wording about this was wrong before the walk.** `AlertRaised` is published on a severity *change*, never per cycle (WP-3.5), so a rule that stays Critical for an hour leaves `occurrence_count` at 1 — confirmed over seven minutes on the live estate. The annotate path is reached by an **escalation** (Warning→Critical) and by a **re-raise after a clear**, not by a problem persisting. Anyone re-walking this needs to drive one of those two.

- **A raise the automation refuses still writes its row.** `SuppressedCount` goes up and `TicketId` stays null, so a storm is legible afterwards. **Expect the consequence:** `AlertRaised` only publishes on a severity *change*, so an alert suppressed by the breaker may never get a ticket at all — the alert itself is unaffected and the monitoring side is where it is visible. That is the breaker working, not a fault.


- **⚠️ A trap for the next bus test: the shared Platform outbox accumulates undelivered rows.** Every test host running on the in-memory bus does `RemoveAll<IHostedService>()`, so its outbox rows are never delivered and simply pile up in the database the whole collection shares — dozens by the end of a run. A later test that publishes for real is queued behind all of them and times out at the default sweep rate. `AlertTicketBusIntegrationTests` sets `OutboxDeliveryServiceOptions` (250 ms, 500 messages) and `MassTransitHostOptions.WaitUntilStarted`, **both registered after `AddPlatformServices` — options configure actions run in registration order, so anything set before it is silently overwritten by MassTransit's defaults.** It passed alone and failed in the full suite, which is the same signature as the WP-3.2 topology trap and the WP-3.4 shared-table trap and is worth recognising on sight.

- **`DeviceReachabilityChanged` is now deliberately *not* consumed, and this reverses what the WP-3.4 note predicted.** It is edge-triggered — one message per transition — so a "for N cycles" condition cannot be evaluated against it without re-deriving cycles it does not carry. Every WP-3.5 rule is therefore per *check* and driven from `DeviceTelemetryReported`, and the ICMP check's **availability** rule answers the reachability question from telemetry that does arrive every cycle. The event remains a fact with no consumer; a device-level roll-up (one dead switch instead of four alerts) belongs to **WP-5.1 root-cause suppression**, which is the package that exists for it.

- **A check has exactly two rules and it matters which metric the second one watches.** `check:{checkId}:availability` (did the check complete — every check has one, needs no configuration) and `check:{checkId}:{metric}` (only where a threshold is configured, and only on `AlertRules.PrimaryMetric` — `icmp.rtt_ms`, `cpu.utilisation_percent`, `memory.used_percent`, a raw OID's own name, `check.latency_ms` for WP-3.8's TCP/HTTP). An SNMP CPU read reports a figure **per core** beside the average, so judging every metric would turn one busy host into nine alerts. **`PrimaryMetric` mirrors the poller's naming by hand — if `services/poller/src/poller/checks/*.py` renames a metric, this silently stops alerting on it** and `AlertRulesTests` is the only thing that would notice.

- **Rule ids are the WP-3.6 contract and are derived, not allocated.** WP-3.6's dedupe key is `alert:{deviceId}:{ruleId}`, which only works because the id comes from the check id and is identical across a restart and on every recurrence. Changing the format is a breaking change to a package that has not been written yet.

- **Redis holds the state machine; Postgres holds the truth, and the seam is tested.** `monitoring:alert-state:{deviceId}:{ruleId}` (JSON, 7-day TTL) carries the N-cycle counters, the flap history and what was last published. On a miss `AlertEngine.LoadStateAsync` rebuilds from the open `monitoring.alerts` row, so a Redis flush costs counters rather than re-raising every alert in the estate. `Evaluate_AfterRedisIsFlushed_DoesNotRaiseTheSameAlertAgain` fails if that rebuild is lost. A Redis outage is logged and swallowed — an alert engine that stops evaluating because a cache is unavailable turns one outage into two.

- **"Raised exactly once" is a database constraint, not only a state-machine invariant**: a filtered unique index on `(device_id, rule_id) WHERE status = 'Open'`. Two consumers racing on one rule cannot both open an alert; the loser's transaction fails and its message is retried against the state the winner left.

- **Publication is driven by a *disagreement*, never by a transition.** The state carries `Severity` (what is true) and `PublishedSeverity` (what anyone was told); a raise or a clear happens exactly when they differ and nothing is suppressing. That single rule is what makes "raised once", "cleared once" and "reconcile after a maintenance window or a flap cooldown ends" one mechanism instead of three — and it is the line to look at first if an alert ever goes quiet or repeats.

- **Suppression withholds the message, not the evaluation.** Inside a maintenance window or while flapping, rules still advance and the alert row is still written and updated (with `suppression` = `Maintenance`/`Flapping` and `is_flapping`), so what happened during a change is legible afterwards. Consequence to expect on a board: **a muted rule that recovers leaves an `Open` row at severity `Ok` until the next reading after suppression lifts**, which is when it reconciles and closes. Also: **the state change that trips the flap threshold is itself withheld** — the message proving a rule is flapping is the kind the policy exists to stop.

- **Alert tuning is five nullable columns on `check_definitions` plus `Monitoring:Alerting` defaults (sustain 3, recovery 2, hysteresis 5%, flap 4-in-600s, cooldown 600s, state TTL 7d).** Null means "the platform default" — a check never stores a copy, so raising the platform's sustain count raises it everywhere nobody asked otherwise. They are set through `alertTuning` on the WP-3.1 check create/update payload, and **that block is a complete statement: omitting it restores the defaults** rather than keeping the previous overrides (the WP-2.2 assignment-endpoint rule).

- **`/api/notification-channels`, `/api/notification-routing-rules`, `/api/notification-deliveries` and `/api/notification-digests/runs` are new and `AdminOnly`; `/api/notification-preferences/me` is new and needs only a sign-in.** None of them has a browser surface — same position as `/api/ci-custom-fields` and `/api/ticket-categories`. **A notification-preferences screen is nobody's WP yet**, and it is the most obviously missing one: the API is per-user and every signed-in role can reach it.

- **`/api/alerts` now exists (WP-3.9)**: list (filtered by status/severity/device/CI/acknowledged, worst first, with estate-wide counts), `GET /{id}` with the full WP-3.7 context, and `POST /{id}/acknowledgements`. `GET /api/monitoring/status-board` sits beside it. Both are behind `CanManageMonitoring`.

- **A second consumer now binds `Contracts.Events:DeviceTelemetryReported`.** `AlertTelemetryConsumer` sits beside WP-3.4's `DeviceTelemetryConsumer` on its own queue, so a faulting alert engine cannot stop metrics being written or the reverse. It **does** use the Platform dedupe helper (unlike WP-3.2's heartbeat) because the state machine counts consecutive readings and a redelivery would advance every N-cycle counter twice.

- **`InfrastructureFixture` now starts a Redis container** and `AlertEngineIntegrationTests` sets `ConnectionStrings__redis` as an **environment variable** as well as in configuration: Aspire's `AddRedisClient` reads the builder's configuration while the host is being built, which is before `WebApplicationFactory`'s `ConfigureAppConfiguration` sources exist — the same reason the WP-3.4 tests set `ConnectionStrings__database` that way. In-memory config alone gives "No endpoints specified".

- **🐞 A WP-3.1 defect found by WP-3.3 and deliberately NOT fixed here: moving a device between poller groups throws a 500.** `MonitoredDeviceService.UpdateAsync` calls `IMonitoringConfigLog.RecordAsync` **twice** in one transaction when `pollerGroup` changes (the upsert against the new group and the removal against the old — the behaviour DECISIONS.md records as deliberate). `RecordAsync` allocates its version from `max(version)` *in the database*, so both calls compute the same number and EF refuses the second with `InvalidOperationException: another instance with the same key value for {'Version'} is already being tracked` — before anything reaches Postgres. **Confirmed with a throwaway integration probe against a real database on 2026-08-10**, and the same collision is what made this session's monitoring seeder fail on its second device. Nothing tests a group move today. **The fix is in `MonitoringConfigLog.RecordAsync`**: allocate from the greater of the database's `max(version)` and the highest version already added to the change tracker (or call `SaveChangesAsync` between records, which is what the seeder does). It was left alone because it is WP-3.1 code and SESSION.md §3.1 says the default is to record and stay in scope — it wants a `fix/` branch and a test that moves a device between groups.

- **The poller's ICMP works through a sysctl, not a capability, and this was the opposite of the plan.** `--cap-add=NET_RAW` does not give a **non-root** container a usable raw socket: Docker puts the capability in the permitted set, and a process with no file capability on its binary has an empty effective set, so icmplib still fails with "Root privileges are required". Probed both ways against the built image. AppHost instead passes `--sysctl net.ipv4.ping_group_range=10001 10001` and sets `POLLER_ICMP_PRIVILEGED=false`; **that number is the Dockerfile's uid and nothing but a failing ping says so if the two drift.**

- **Telemetry is now ingested; `DeviceReachabilityChanged` still has no consumer.** WP-3.4 bound `DeviceTelemetryConsumer` to `Contracts.Events:DeviceTelemetryReported` and — exactly as the WP-3.3 note predicted — it started receiving with no poller change at all. `Contracts.Events:DeviceReachabilityChanged` is still a fanout with nothing bound — **and WP-3.5 decided not to bind it either; see the note above.** Up/down history is nevertheless queryable, because ingestion derives a `check.success` 0/1 series from every check result.

- **⚠️ WP-3.4 broke a WP-0.5 test and the fix was to narrow that test's assertion, not to change the consumer.** `MessageBusOutboxIntegrationTests.Outbox_BusStartsAfterPublish_...` asserted `platform.consumer_dedupe_entries` was **globally empty** before the bus started — true only while `SystemPingConsumer` was the helper's one user. `DeviceTelemetryConsumer` now writes a row per poller cycle into the database the whole test collection shares, so the assertion started failing on test *order*. It passed alone and failed in the suite, which is the same signature as the WP-3.2 topology trap and is worth recognising on sight. It now asserts only its own `system-ping:` key. **Any future consumer using the dedupe helper is fine; any future test asserting that a shared Platform table is empty is not.**

- **Nothing in application code ever deletes a metric.** Retention (raw 30 days, 5-minute rollup 1 year) and the rollup's refresh are **Timescale background jobs**, installed by the WP-3.4 migration as raw SQL and owned by the database's own scheduler. Consequence: they keep running when the host is down, they do not appear in any C# you can grep for, and `timescaledb_information.jobs` is where you look when data is missing or not aging out. Chunks are **one day** wide, which is also the granularity at which the 30-day policy actually removes anything.

- **`monitoring.device_metrics_5m` is a continuous aggregate with real-time aggregation deliberately turned back on.** Timescale defaults `materialized_only` to true from 2.13; the refresh policy runs every five minutes with a five-minute end offset, so the default would leave the newest 5–10 minutes missing from every long-range chart — the part somebody is actually watching. The `ALTER MATERIALIZED VIEW ... SET (timescaledb.materialized_only = false)` in the migration is load-bearing and easy to lose in a rewrite.

- **The `check.` metric-name prefix is reserved and a poller-supplied sample using it is dropped.** Ingestion derives `check.success` (0/1, and the average over a bucket is availability) and `check.latency_ms` from every check result, including a failed one — a failed check carries no samples of its own, so without this an unreachable device would be indistinguishable from one nobody polls. If a future poller wants to report its own success metric, it needs a different name.

- **🐞 A WP-3.4 defect found by hand-verification and fixed (2026-08-10): a metric name is not a series — a metric name *plus a check* is.** Ingestion derives `check.success` and `check.latency_ms` from **every** check, so the seeded four-check router reports each of those names four times. The first query API filtered on device + metric name only, and returned all four interleaved: on the live estate, ICMP latency of 0.03 ms plotted next to SNMP latency of 522 ms as one line. Storage was never wrong (the natural key carries `check_id`, and the rollup groups by it) — only the read path was. **Now:** `GET .../metrics/series` takes an optional `checkId`, refuses with 400 naming the candidates when the metric is ambiguous and no check is named, and resolves it silently when only one check reports it; the picker lists one entry per (metric, check) with the check's name. **Every test had used one check per device, which is exactly why the suite was green.** `Series_ForAMetricSeveralChecksReport_IsRefusedUntilOneIsNamed` fails if this comes back.

- **A raw-resolution series longer than 24 hours is a 400, not a truncated chart.** `resolution=Auto` (the default) reads raw up to 6 hours and the 5-minute rollup beyond it; asking for `Raw` over a month is refused with a sentence naming the alternative. Same rule as WP-2.3's traversal cap: a partial answer must never look like a complete one.

- **The metrics hypertable has no foreign key to `monitored_devices`, and `device_inventory_facts` does.** A reading is a fact about a moment and stays true after the device row is deleted (and Timescale drops chunks out from under the table anyway); a "what model is this switch" fact is current state and goes with its device. The consequence is that ingestion filters inventory facts against existing devices before writing — a device deleted between the poll and its ingestion would otherwise fail the whole batch.

- **The metric picker is discovered from the data, not declared.** `GET /api/monitored-devices/{id}/metrics` is a `DISTINCT ON (metric_name, check_id)` over the last two days, so a metric that has stopped being reported disappears from the picker rather than charting a flat line. Nothing in the SPA reads any of the three new endpoints yet — WP-3.9 is their intended caller.

- **The poller's broker credential now grants three exchanges, not one.** `RabbitMqDefinitions.PollerExchanges` is the whole permission model in one list, and the write pattern is an anchored alternation of those literal names. A prefix pattern (`^Contracts\.Events:.*$`) is the obvious shortcut next time an exchange is added and is a licence to forge a `TicketCreated`; `Render_PollerWritePattern_DoesNotMatchAnotherEventsExchange` fails if anybody reaches for it. `configure` and `read` are still empty.

- **A monitoring seeder now exists (3 devices, 8 checks) and it is the first seeder that must write through a service-layer helper.** A device written without an `IMonitoringConfigLog.RecordAsync` in the same transaction is invisible to every poller forever — including to a full snapshot, which is built from the same log — and looks from the outside exactly like a broken poller. `MonitoringDemoSeederIntegrationTests` asserts a config-change row per device. This is a departure from WP-2.8's "seeders write through the DbContext"; the two are not separable here.

- **snmpsim was pulled forward from WP-3.12.** One container (`tandrup/snmpsim`, `src/AppHost/snmpsim/*.snmprec`) serves two device profiles by community string — `healthy` and `degraded` — so the seeded estate has a quiet device and a struggling one without a second container. `docker stop` on it is the "target goes away" step. The recordings are plain text and **must stay sorted by OID** or snmpsim refuses to index them. WP-3.12 still owns the mock HTTP target and the E2E test.

- **The simulator is addressed as `snmpsim:161` on the Aspire session network, and publishing a host port for it is the wrong answer.** The first live walk of this package seeded `host.docker.internal:1161` and every SNMP check timed out: Aspire proxies a published endpoint through DCP, which binds **loopback**, so the port answered from the host and not from the poller's container — the same trap WP-2.7 hit with the pinned SPA/API ports. The resource therefore declares **no endpoint at all**; the poller and the simulator are containers on one network and Aspire's resource name resolves there. **Anything else that needs to reach a dev-only container from another container should do the same rather than reach for `WithEndpoint`.** Consequence for verification: stopping the simulator now takes its ICMP *and* SNMP checks down together, because the name stops resolving — a cleaner "the device went away" than the host-address version, which kept answering pings.

- **Nothing in this package evaluates a threshold.** Warning and critical values travel to the poller and are not read by it. WP-3.5's state machine consumes the telemetry instead, which is also why maintenance windows are still fetched and still ignored: a poller that stopped measuring during a window would leave a hole in the metrics exactly where a change was being made.

- **⚠️ The Phase 2 gate's two non-demo tasks are still outstanding.** The manual checklists were walked and accepted (2026-08-10), and Phase 3 has started, but **`v0.3-phase2` was never tagged** and **`aspire update` was never run** — both were part of the gate. Tagging retroactively means picking a commit; `04e0f82` (WP-2.11) is the last Phase 2 commit and is the honest choice. The `aspire update` should happen on its own branch, not folded into a feature package.

- **A monitored device is a CI plus an address, and nothing stops that CI being deleted (WP-3.1).** `assets.ci` delete is guarded against relationships (WP-2.3) and ticket links (WP-2.4), but not against `monitoring.monitored_devices` — that would need an `IMonitoredDeviceDirectory` port in `Platform/Integration` implemented by Monitoring, and the WP text did not call for it. Consequence today: deleting a monitored CI leaves the device pointing at nothing, and its `CiName` reads null on the device list and in the poller config. **The port is the fix, and it belongs to whichever WP first cares.**

- **Config deltas are per *device*, not per field or per check.** A check edit re-sends its whole device; the poller's unit of work is a device. `PollerConfigDeltaPlanner` decides "changed" against "removed" purely by whether the device is *currently* enabled and in the poller's group — so deleting, disabling and moving a device between groups all come out right without the planner reading the change kind. A device that moves groups deliberately writes **two** rows (upsert against the new group, removal against the old).

- **Config versions are allocated by the application under `pg_advisory_xact_lock`, not by a sequence or identity column.** This is deliberate and load-bearing: identity values can commit out of order, so a poller reading `max(version)` while a lower version was still uncommitted would never see that change again. Every write in the module must therefore call `IMonitoringConfigLog.RecordAsync` **inside its own transaction** — the lock is transaction-scoped. Anything that writes devices or checks outside these services and skips it will be invisible to every poller.

- **`GET /api/pollers/{name}/config` writes.** It records `last_config_version`/`last_config_fetched_at` on the poller row. It is the only write behind a GET in the module and it is deliberately **not** audited — a poller reading its own config has no before/after entity state. WP-3.2's heartbeat is the consumer of those two columns.

- **⚠️ Two real defects in WP-3.2 were found by verification and fixed (2026-08-10). Both had shipped looking correct and both passed the original test suite.** (1) **The Python poller's MassTransit envelope carried `sourceAddress`/`destinationAddress`, and MassTransit parses those as absolute URIs during deserialisation, before any consumer runs.** `exchange://Contracts.Events:PollerHeartbeat` reads as a host and a port, so every heartbeat dead-lettered with `System.UriFormatException: Invalid URI: Invalid port specified` — the poller logged "Heartbeat published", the broker accepted it, and 36 beats went to `PollerHeartbeat_error` while nothing on either side looked wrong. **Both fields are now omitted** (they are optional and carry nothing the consumer needs; the poller names itself in a `poller-source` header). The gap that let it through was that no test ever read the other language's output — now `services/poller/tests/fixtures/heartbeat-envelope.json` is a committed fixture asserted on the Python side by `test_bus.py` and on the .NET side by `PollerEnvelopeTests`, which checks the message URN, deserialises the payload with MassTransit's own serializer options, requires every property of the contract to be present, and requires every address field to be absent or an absolute URI. **Any future field on that envelope has to survive both.** (2) **The heartbeat's monotonic guard compared a `DateTimeOffset` at 100ns tick precision against a `timestamptz` truncated to microseconds**, so a redelivered beat looked newer than itself and was applied twice — the same precision trap the WP-3.1 note records, in production code rather than in a test. Both sides are now truncated to stored precision before comparing.

- **`PollerBusCredentialIntegrationTests` starts a RabbitMQ container of its own and must keep doing so.** It imports the rendered definitions document, and an import is a broker-wide act — run against the shared `InfrastructureFixture` broker it silently took the topology out from under `PollerHeartbeatBusIntegrationTests`, whose MassTransit endpoint then never finished starting and whose heartbeats never arrived. The symptom was a test that passed alone and failed in the full suite with no error queue and no dead letters, which is what "the topology moved" looks like from the outside. **Nothing else may import definitions into the shared broker**; the helper that used to make that easy was deliberately removed from `InfrastructureFixture`.

- **The poller now has an identity of its own, and `CanPoll` is disjoint from every operator policy.** `POST /api/pollers/registrations` and `GET /api/pollers/{name}/config` require the `Poller` realm role — **not Admin, not Technician** — while `GET /api/pollers` stays on `CanManageMonitoring` and is refused to a poller. Consequence for hand-verification: those two endpoints can no longer be curled with a user token; get a poller token with `client_credentials` against `it-platform-poller` (secret: `dotnet user-secrets list --project src/AppHost | grep poller-client-secret`).

- **Keycloak's issuer is now pinned with `KC_HOSTNAME`, derived from `public-host`.** Before WP-3.2 every client called Keycloak by the same name it was configured with, so the issuer was right by accident; the poller runs in a container and must dial `host.docker.internal`, which would otherwise mint a token the API rejects as `invalid_token`. If a future resource cannot reach Keycloak, this is the setting to look at first — and it must stay in step with `public-host`, exactly like the realm's redirect URIs.

- **The RabbitMQ broker is now provisioned from a rendered definitions file, and the poller's account is publish-only.** AppHost writes `src/AppHost/obj/rabbitmq/definitions.json` (accounts, permissions, and the heartbeat exchange) plus a `conf.d` snippet pointing at it. The renderer is `Platform/Messaging/RabbitMqDefinitions.cs` **so the tests import the shipped document rather than a copy** — `PollerBusCredentialIntegrationTests` proves the poller can publish the heartbeat and cannot declare, consume, or publish anywhere else. The document contains the *platform's* account too: a definitions import can otherwise suppress the image's default-user creation, and both accounts have to survive a boot.

- **The heartbeat exchange is declared by the definitions file, not by the poller**, because the poller has no `configure` permission. Its name, type (`fanout`) and durability must match what MassTransit declares for `Contracts.Events.PollerHeartbeat` or the API's bus start-up fails with PRECONDITION_FAILED. `RabbitMqDefinitionsTests` compares it against `MessageUrn.ForType<PollerHeartbeat>()`, so renaming or re-namespacing that event breaks a test rather than the running stack.

- **The heartbeat consumer does not use the Platform dedupe helper, and that is deliberate.** It is idempotent by construction: the stored heartbeat only ever moves forward, so a redelivery or an overtaking message is a no-op. A dedupe row per beat would be one row every 15 seconds per poller, forever, to protect an update that is already safe to repeat. **This is a departure from ARCHITECTURE.md §4's "use the Platform dedupe helper" and the only one in this package** — a future consumer of poller telemetry should not copy it without the same argument.

- **Module consumers are registered through a new optional `configureBus` callback on `AddPlatformServices`.** MassTransit is configured once per host, but a consumer belongs to the module that reacts, and Platform may not reference a module. `Web.Host/Program.cs` passes `MonitoringServiceCollectionExtensions.AddMonitoringConsumers`; the next module with a consumer adds its own the same way.

- **`PollerHeartbeatMissed` is a fact, not an alert.** Nothing consumes it yet. **WP-3.5 did not consume it either** — its rules are all per monitored *check*, and a poller going quiet is a fact about the platform rather than about a device. WP-3.6's ticket automation remains its intended consumer; the evaluator deliberately does not raise an alert, open a ticket or notify anyone. What it does do is write an audit entry (`Poller` / `HeartbeatMissed`), which is also what flushes the outbox.

- **Detection is "two of the poller's own intervals, plus up to one evaluation tick".** Defaults: poller cycle 15s, `Monitoring:Heartbeat:MissedThreshold` 2, `Monitoring:Heartbeat:EvaluationIntervalSeconds` 10 — so a stopped poller is reported 30–40s after its last beat; the live walk measured **37.7s, i.e. 2.5 cycles**. **The WP text asks for "within 2 cycles" and that is not literally achievable with a two-beat threshold** — the threshold is not crossed until 2 cycles have elapsed, so any detection is necessarily later than that. Dropping the evaluation interval to 5s narrows it to 30–35s; going below two cycles means lowering the threshold, which is what makes a single slow cycle an outage. The interval is the poller's, reported on each beat, so a slow poller is judged by its own cycle. **A poller that has never sent a heartbeat is never reported**: it has no interval to be late by, so a registration that never started is silent rather than alerting.

- **The poller is a container built from `services/poller/Dockerfile` via `AddDockerfile`, not an Aspire Python resource**, so `docker stop` is a real verification step. It exposes no endpoint and holds two credentials (the OIDC client secret and the AMQP URL), both injected by AppHost from generated persisted parameters. It was run under a live `aspire run`, stopped with `docker stop`, and restarted — registration, config fetch, heartbeat, silence detection and recovery all confirmed end to end.

- **The poller never crashes on a failed cycle, and never clears its configuration because of one.** A failed registration, config fetch or publish is logged and the cycle continues with what it already held. The one exception is start-up: a missing environment variable is fatal by design. A rejected `sinceVersion` makes it forget everything and take a full snapshot in the *same* cycle rather than the next.

- Disposed CIs are frozen: `PUT /api/cis/{id}`, the assignment endpoint, and any further transition all return 409. Nothing in the UI can un-dispose a CI, which is deliberate.
- `CanManageAssets` (Admin/Technician/Manager) is a new authorization policy added by WP-2.1. It is additive — the existing `AdminOnly` and `CanManageTickets` policies are untouched.
- Dev Postgres resets between `aspire run`s whenever AppHost configuration changes (the unnamed `.WithDataVolume()` name embeds a config hash, so a new empty volume is mounted). This is **intentional** — see DECISIONS.md. Consequence: anything created through the API by hand is gone after a restart, so demo/verification fixtures must live in the seeder.

Seeded: the one allowlisted runbook plus a trigger **scoped to the mock HTTP target alone**. **No browser surface** — the WP names none and the operator-visible half is the ticket comment. **Its checklist has NOT been walked** — see In flight
- [x] WP-5.7 Problem mgmt + recurrence (2026-08-17) — **a problem links incidents, a known error is a *state with an entry condition*, and a nightly pass suggests rather than decides.** `helpdesk.problems`, `problem_incidents` (a real FK both ends, unlike a ticket↔CI link) and `problem_suggestions`. `ProblemStatus` is `Investigating → KnownError → Resolved → Closed`, reopenable from anywhere, and **`KnownError` is reachable only with both a root cause and a workaround recorded** — that condition is what makes the known-error list worth searching, and erasing either field puts the problem back to Investigating. Transitions go through `POST /api/problems/{id}/transitions` (a missing field is 400, a move the workflow does not make is 409). **Closing one answers with a knowledge-article draft** — symptoms deduplicated from the incident titles and counted, cause, workaround, resolution, incident numbers — carried inline on the response so the prompt cannot be lost; WP-5.9 owns the KB and nothing here stores an article. **Detection**: a pure `RecurrenceDetector` beside a service that counts, giving a verdict for *every* candidate (not just the survivors) so the pass can say why it stayed quiet; four silences — below threshold, already an **open** problem, already suggested, dismissed inside a cooldown. "One open suggestion per subject" is **two filtered unique indexes**, not an ordering assumption. Accepting one opens the problem and links **every incident on the subject since the window opened**. `ProblemDetectionJob` runs daily from start-up (idempotent, like the contract-expiry pass), and `POST /api/problem-suggestions/detect` runs it by hand so the WP's first verification step is walkable in a session. **Browser**: `/problems` (board + known-error filter + the recurrence inbox on the same screen), `/problems/{id}`, and a `RelatedProblemsCard` on the ticket screen that **renders the workaround in full** — a known-error database that does not reach the person holding the ticket is one nobody reads. Agent-only throughout: `CanManageTickets` includes EndUser for the portal, so every method checks `ActorRoles.IsAgent`. Seeded: five incidents on one network CI, **exactly the default threshold**. **Its checklist has NOT been walked** — see In flight
- [x] WP-5.8 Maintenance sync (2026-08-17) — **a change request over CIs in Assets, and the maintenance window its approval opens in Monitoring, joined by an event and never by a port.** `assets.change_requests` + `change_request_cis`; `ChangeWorkflow` is a table (`Draft → Submitted → Approved/Rejected/Cancelled`, with `Submitted → Draft` the one backwards arrow so a slot that expires while awaiting a decision is not a dead end). It lives in Assets rather than Helpdesk because "+ dependents" is a walk of `assets.ci_relationships`, which only this module may read. **Three entry conditions on approval:** it covers at least one CI, its planned **end** has not passed (the start may have — a change approved as the work begins is the normal case), and **nobody approves their own change** (403, enforced in the workflow because it is a question about a record, not a role). Approving publishes `ChangeRequestApproved` **through the outbox**, carrying the CI set with dependents already resolved — **once, at approval, frozen**, so an edge added overnight cannot widen a window somebody agreed to. Monitoring's `ChangeRequestApprovedConsumer` maps those CIs to its own devices and calls `CreateForChangeAsync`, so the window is validated, config-logged for the pollers and audited like any other; **a change covering nothing monitored opens no window at all, never an estate-wide one**. Idempotent twice over: the Platform dedupe helper on the consumer, and a **filtered unique index on `change_request_id`**. **Suppression itself needed no new code** — `AlertEngine.MutedDevicesAsync` already mutes on an active window and un-mutes when it ends, because status is computed against the telemetry's clock rather than stored — so this package **proves** it instead: an approved change's window silences a real breaching device, and the same device alerts exactly once when the window ends. `ChangeRequestCi.CiId` is `Restrict`, with a matching guard in `CiService.DeleteAsync` so it comes back as a 409 that names the obstacle. **Browser:** `/changes` (month calendar drawing changes *and* the windows they opened, an entry on **every day it spans**, plus a new-change dialog) and `/changes/{id}` (coverage with dependents marked, the decision, and the live window). Action buttons read `nextStatuses` **off the change** rather than duplicating the workflow — WP-5.7's own note about a button nobody is offered. Seeded: **one draft change on the WP-3.12 down-able switch**, so the WP's verification is two buttons on a fresh `aspire run`. **Its checklist has NOT been walked** — see In flight
